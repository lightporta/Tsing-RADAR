# Tsing-RADAR 前两版基础上的改动与当前开发状态总结

日期：2026-07-31

## 一、总体结论

当前版本以原始 `Tsing-RADAR` 为主线，没有直接覆盖合并 `tsing-radar-patched`，而是选择性吸收 patch 中正确的协议方向，再重新实现其未完成或存在安全问题的部分。

项目已经从“界面和工程骨架较完整、主要业务为 Mock 或占位”的演示原型，发展为“核心站内闭环可在本地真实运行、具有数据治理和安全测试的候选版本”。A1–A7 与 D1 已完成本地实现和独立审计，但尚未部署、没有生产数据，也不能称为生产可用。

最需要明确的一点是：

- 清小搭兼容的智能体 API 已经实现，并通过本地合同测试；
- GLM/DeepSeek 的外部模型调用适配器已经编写；
- 但当前环境没有配置模型密钥，真实外部模型没有完成联网调用验证；
- 当前主访谈和推荐链路使用服务端状态机、结构化画像、确定性词法/概念召回与多目标排序，不是由大模型直接生成推荐；
- 简历和匹配报告使用确定性模板生成，不调用大模型补写经历。

因此，当前状态应表述为：**智能体接口和可信业务内核已经实现，但真实大模型尚未在当前环境的主链路中接通和验证。**

## 二、相对初版 radar 的主要更改

### 1. 从演示架构升级为双入口共享业务内核

初版已经有 Vue 3、FastAPI、三栏工作台、导师卡片、雷达图、散点图、个人信息页和信息平台页，但大量数据来自 JSON、前端 Mock、内存变量或占位接口。

当前版本保留了初版的主要视觉结构，同时改成两种入口共享同一套领域服务：

- 清小搭入口：通过 OpenAI-compatible `/v1` API 完成对话、画像确认和匹配结果解释；
- Web 入口：负责访谈、画像编辑、推荐比较、图表、招募信息、简历和行动记录；
- 两个入口共用访谈、画像、匹配、证据和身份授权逻辑，不在协议层复制排序代码。

### 2. 增加真正持久化的动态访谈

初版更接近固定问卷或根据当前一句话立即推荐。当前版本新增：

- 持久化访谈会话；
- 每轮只询问一个高信息量问题；
- 六类学生需求画像；
- 自然语言硬约束草稿；
- 地点、时间、学历阶段、语言、保密和毕业安排等约束的逐项中文确认；
- 可编辑的结构化画像；
- 画像版本冲突检查；
- 用户显式确认后才允许进入匹配。

### 3. 重写导师匹配逻辑

初版的六维雷达重合度、热门度和行业性质主要用于演示，其中不少导师特质和评分缺少来源。

当前匹配顺序改为：

1. 结构化硬约束过滤；
2. 可插拔召回；
3. 可配置多目标排序；
4. 证据化解释；
5. 输出反证、不确定性和待核实问题。

当前默认召回是确定性的词法/概念回退，明确不把它包装成真正的语义 embedding。排序还把以下指标分开：

- 适配程度；
- 证据覆盖率；
- 证据置信度；
- 保守排序分。

这样可以避免资料稀疏的导师因为“只在少数维度得分较高”而被错误奖励。

### 4. 增加证据治理和隐私控制

当前版本为导师和招募信息增加：

- 字段级来源；
- 抓取或观察时间；
- 审核状态；
- 发布状态；
- 授权和同意范围；
- 有效期；
- 下架状态；
- 证据置信度；
- 面向客户端的引用脱敏。

81 条旧导师记录因为来源或授权不足，全部处于受限状态，未发布记录为 0。旧数据中的主观评分、热门度、联系方式、项目和招募信息被隔离，不再作为真实推荐依据。

### 5. 增加官方 2027 博士目录本地数据集

D1 从清华官方入口建立了普通博士目录和推荐免试目录两个独立快照，包括：

- 110/110 个可访问院系；
- 361 个专业；
- 1,743 个研究方向；
- 4,064 个院系范围内的导师或导师组标签；
- 7,688 条方向—导师/导师组目录关系；
- 632 条备注。

该数据集保存字段级公开来源、抓取时间、原始片段、规范化值和内容哈希，并处理了同名导师、跨方向关系和导师组。

这批数据只能证明官方目录中出现的事实，不能推断真实名额、当前一定招生、导师风格、经费、组内氛围、热门度或推荐准确率，也没有被冒充为导师个人画像。

### 6. 增加身份、对象授权和文件安全

初版和 patch 曾依赖固定 `anonymous`、自报学号或原始 Token。当前版本已经改为：

- Web 使用服务端生成的高熵 opaque 会话主体；
- 清小搭只有在终端用户 claim 可验证时才允许稳定绑定主体；
- 无可信 claim 时按请求隔离，不跨请求复用画像；
- 请求体中的 `student_id`、`publisher_name` 或 `owner_id` 不参与授权；
- 会话、画像、匹配、反馈、文件和站内投递均执行对象级授权；
- 原始 Token 不作为业务 ID，不进入数据库。

### 7. 增加真实私有文档能力

当前版本已经支持：

- PDF/DOCX 私有上传；
- 扩展名、MIME、magic 和压缩结构检查；
- PDF 页数、文本量和解析时间预算；
- 文件扫描状态；
- PDF/DOCX 内容解析；
- 确定性生成真实简历和匹配报告；
- 一次性 Web 下载授权；
- 有上限的清小搭附件授权；
- CSRF、显式确认和持久化幂等；
- 删除状态机、授权撤销和失败重试；
- 不包含 Token、文件正文和原始文件名的安全审计事件。

### 8. 增加项目专用 Skill 和验收体系

新增 `skills/build-tsing-radar` 项目 Skill，其中包含：

- 分批批准和实施边界；
- 导师及招募数据合同；
- 清小搭协议合同；
- 导师来源审计脚本；
- 清小搭合同检查脚本。

此外建立了 A1–A7、D1 的规划、迁移、测试和验收文档，防止未批准功能、未授权数据或未经验证的生产声明混入实现。

## 三、相对 patch 改版的主要更改

patch 提供了一些正确方向，包括 SSE 改用 `choices[0].delta`、增加 `[DONE]`、请求体改为 `messages`、后端导师分页、训练密钥移到 Header 等。当前版本保留并完成了这些方向，但没有直接采用 patch 的整套实现。

### 保留并完善的内容

- OpenAI 风格的消息结构；
- 流式 SSE；
- `[DONE]` 结束帧；
- Header 鉴权方向；
- 后端限制返回数据量；
- 前端真实解析流式响应；
- 前后端错误状态处理。

### 重新实现或修复的内容

- 同时支持 `stream=true` 和 `stream=false`；
- 增加标准 `usage`；
- `/v1/models` 和 `/v1/chat/completions` 均要求 Bearer 鉴权；
- 增加严格布尔值和合法 `finish_reason`；
- 多模态消息支持结构化文本和 URL 内容；
- 增加 SSRF、DNS/IP、重定向、大小、类型和超时保护；
- 修复缺 Token 时固定落到 `anonymous` 的跨用户风险；
- 修复原始 Token 被当作学生 ID 的问题；
- 恢复并扩展数据库迁移和数据初始化链路；
- 修复 `synergy` 类型删除后前端仍引用的问题；
- 修复旧聊天请求体与后端协议不一致导致的 422；
- 修复“后端分页、前端仍全量下载再切片”的表面分页；
- 修复只有成功提示、不调用真实投递接口的假闭环；
- 修复附件只有相对 URL、没有安全下载和授权消费的问题；
- 补齐协议、身份、并发、隐私、文件和端到端回归测试。

patch 只对少量前端文件进行了修改，没有真正重做界面。当前版本也没有推翻初版 UI，而是在原有三栏工作台和两个二级页面上补齐真实 API、空状态、失败状态、移动端适配和可访问性。

## 四、当前人工智能与 API 的真实状态

### 1. 清小搭智能体 API

已实现：

- `GET /v1/models`；
- `POST /v1/chat/completions`；
- 非流式响应；
- 流式 SSE；
- Bearer 鉴权；
- `usage`；
- 多模态 URL 输入；
- 访谈、画像确认、匹配和证据解释；
- 本地协议合同测试。

未完成：

- 没有公网部署；
- 没有真实 `QXD_API_KEY` 和终端用户签名密钥；
- 没有在清小搭真实生产入口完成端到端探测；
- 官方附件能力仍需在真实平台开放和部署后验证。

### 2. 外部大模型 API

代码中已经编写 GLM 和 DeepSeek 的真实 HTTP 调用适配器，GLM 失败时可降级到 DeepSeek；embedding 接口也可以在有 GLM 密钥时调用真实向量服务。

但当前工作区和进程环境均未配置：

- `GLM_API_KEY`；
- `DEEPSEEK_API_KEY`；
- `QXD_API_KEY`；
- `QXD_END_USER_SIGNING_SECRET`；
- `PUBLIC_BASE_URL`。

同时，`llm_complete()` 当前没有被主业务路由调用。Web 访谈和清小搭对话实际调用的是访谈状态机与共享匹配服务。A4 默认匹配也不调用 embedding，而使用确定性词法/概念召回。

因此：

- “外部模型适配代码已经写好”——是；
- “当前系统已经真实调用 GLM/DeepSeek”——否；
- “清小搭协议接口已经在本地实现”——是；
- “已经与公网清小搭完成真实互操作”——否；
- “当前推荐由大模型或深度学习模型生成”——否。

这样的设计保证了确认门、硬约束和证据边界不会被模型绕过，但用户最初设想的“更有洞察力的 LLM 追问、简历智能打磨、真正语义召回”仍需要后续接入和效果评估。

## 五、信息平台开发情况

### 已经完成

- 前端默认 `VITE_USE_MOCK=false`，列表调用真实后端；
- 展示已审核、已发布且未下架的招募信息；
- 急需信息置顶和筛选；
- 用户可以提交实习、招生或科研助理信息；
- 提交者身份由服务端会话绑定，不信任前端自报身份；
- 新提交默认进入 `pending_review/restricted`，审核前不公开；
- 用户可以查看和删除自己尚未发布的投稿；
- 学生可以从自己的私有 PDF/DOCX 中选择简历；
- 可创建幂等的站内投递记录；
- 可查看状态并撤回站内投递；
- 文件归属、招募状态和对象引用都有授权与并发保护。

### 尚未完成

- 没有完整的管理员审核、驳回、发布和下架操作界面；
- 没有正式的发布者角色认证；
- 没有真实已审核的招募内容基线；
- 没有站内通知或双方消息系统；
- 没有将简历实际发送给导师、邮箱或第三方；
- 没有外部联系或外部招聘平台集成；
- 没有验证真实运营环境下的过期清理、审核时效和大数据量分页。

当前信息平台可以评价为：**站内投稿和行动记录闭环已经成型，但内容审核、正式发布和外部投递的运营闭环尚未完成。**

## 六、个人信息与简历管理开发情况

### 已经完成

- 个人信息页面包含姓名、院系、类别、年级、GPA、邮箱、电话、科研经历和兴趣标签；
- 提供六维需求权重编辑；
- 客户端不再使用学号或模拟登录参与身份认证；
- 姓名、年级、电话等信息不写入 `localStorage`；
- 普通个人信息表单只保留在当前页面内存，刷新后清除；
- 动态访谈生成的结构化学生画像单独持久化在服务端；
- 支持私有上传、查看、下载和删除 PDF/DOCX；
- 支持根据用户明确填写的信息生成真实 PDF/DOCX 简历；
- 支持生成匹配报告；
- 支持查看和撤回站内投递记录；
- 下载使用会话、CSRF 和一次性授权，不公开文件 URL。

### 尚未完成

- 普通个人信息表单与访谈画像是两套数据源，尚未统一；
- 普通个人信息刷新后丢失，没有经用户授权的服务端长期资料；
- 没有真实清华 SSO 或正式账户体系；
- 没有跨设备资料同步；
- 没有完整的资料导出、撤销同意和保留期限管理界面；
- 没有调用大模型解析上传简历并自动提取经历；
- 没有真正的 LLM 简历润色、措辞优化和定向导师包装；
- 当前简历生成只排版用户明确填写的信息，不补写事实；
- 尚未使用真实私有 S3 和真实 ClamAV。

当前个人信息模块可以评价为：**隐私边界和私有文件闭环较完整，但统一画像、长期资料管理和 AI 简历助手仍未完成。**

## 八、需要进一步测试并据此更新的部分

### 第一优先级：真实 API 和主智能能力

1. 配置受控测试密钥，验证 GLM/DeepSeek 对话和 embedding 的真实连接、超时、限流、失败降级和成本。
2. 明确大模型在主链中的职责，建议只用于自然语言理解、追问措辞和证据摘要，画像确认、硬约束和发布门继续由服务端控制。
3. 将 `llm_complete()` 接入一个受约束、可回退的真实业务位置，并补结构化输出、幻觉和提示注入测试。
4. 部署到获批测试环境后，完成真实公网清小搭协议探测和多轮会话验证。
5. 对“确定性词法召回”“真实 embedding”“混合召回”进行同一标注集的离线对比，验证后再决定是否切换默认方案。

### 第二优先级：真实数据和推荐效果

1. 建立经过授权和审核的导师个人画像数据；当前发布导师为 0，无法产生真实推荐。
2. 为热门/蓝海机会信号建立真实来源、时间窗、更新频率和失效机制。
3. 使用人工标注的真实或获批匿名样本测试硬约束、同义改写、无关高词面重合和排序解释。
4. 开展小规模用户测试，评估追问质量、画像正确率、推荐可用性和用户是否理解不确定性。
5. 反馈和访谈完成状态不能直接作为学习排序标签；只有获得合规的真实结果标签并完成偏差、泄漏和隐私检查后，才能启用深度学习或学习排序。

### 第三优先级：信息平台运营闭环

1. 增加管理员审核、驳回、发布、下架和审计界面。
2. 验证发布者资格、授权材料、联系方式展示范围和过期自动下架。
3. 测试大数据量下的服务端分页、搜索和筛选。
4. 增加站内通知和状态流转；是否允许真实发送简历必须由用户另行批准，并增加更严格的确认与审计。

### 第四优先级：个人资料统一

1. 合并页面表单与访谈画像，避免姓名、兴趣、约束和权重出现两个版本。
2. 明确选择“仅会话保存”还是“用户授权后服务端长期保存”，并据此完善刷新、过期和跨设备体验。
3. 验证资料删除、导出、撤回授权、会话过期和多用户隔离。
4. 在接入 AI 简历解析或润色前，先定义不得编造经历、逐项确认修改和原文不外泄的合同。

### 第五优先级：发布环境安全和稳定性

发布前仍需完成：

1. 真实 PostgreSQL 双连接投递/删除竞争测试；
2. Office 或 LibreOffice 的 DOCX 逐页视觉验收；
3. 对象读取硬上限或流式读取；
4. 真实 ClamAV 可用性和失败关闭验证；
5. 真实私有 S3 的读写、权限和加密验证；
6. 公网 DNS、TLS、可达性和部署侧 SSRF 复核；
7. 反向代理/CDN 的签名 Token 日志脱敏；
8. 生产日志 sink、保留策略、告警和访问控制；
9. 发布内容、Git 历史和对照目录的数据泄露审计；
10. 真实公网清小搭端点探测。

## 九、建议的下一步顺序

建议按以下顺序继续，避免在没有真实数据和真实 API 的情况下先优化界面：

1. 受控接入并测试真实 LLM；
2. 完成信息平台审核发布后台；
3. 统一个人资料与访谈画像；
4. 引入少量经授权的导师和招募数据；
5. 开展人工效果测试并更新追问、召回和排序；
6. 最后进入真实基础设施和公网清小搭验收。
