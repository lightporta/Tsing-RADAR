## 二、接口接入效果

### 2.1 新接口（事实类，全部 `derived_signal=false`）

| 接口 | 用途 | 关键字段 |
|---|---|---|
| `GET /api/advisors` | 已发布导师列表（分页 + 院系过滤） | `entity_id` / `department` / `title` |
| `GET /api/advisors/{entity_id}` | 导师详情 + 顶层 evidence | 含 6 字段 + directions |
| `GET /api/advisors/{entity_id}/directions` | 研究方向（带 scope） | current_official / catalog_only / historical |
| `GET /api/advisors/{entity_id}/opportunities` | 公开机会（自动过滤过期） | valid_until 校验 |
| `GET /api/advisors/{entity_id}/evidence` | 字段级证据（可追溯） | source_url / source_class / captured_at |
| `GET /api/catalog/{year}` | 年度招生目录 | 强制 disclaimer |

所有接口统一返回：
```json
{
  "code": 0, "message": "ok", "data": {...},
  "evidence": {"source_url": "...", "source_class": "A", "captured_at": "...", "evidence_id": "..."},
  "derived_signal": false,
  "disclaimer": null
}
```

### 2.2 旧接口（兼容层，未破坏前端）

- `GET /api/mentors` 与 `/api/mentors/sort` 通过 `load_mentors_with_fallback()` 工作：
  - 数据库可用且有 `published` 记录时，从 9 表投影成旧格式（含 `entity_id` 新字段）
  - 数据库不可用或无 `published` 时，降级到 `mentors.json`
- **改造建议**（生产期）：`/api/mentors` 中 `radar_traits` / `popularity` / `score` 等派生字段已留默认值，应由 `/api/match` / `/api/scatter` 单独计算并标注 `derived_signal=true`（Agent-3 改造清单已就位）。

### 2.3 发布门禁（强制 workflow）

所有数据进入公开层必须经此流程：

```
build_database.py        → batch JSON (全部 withheld)
        ↓
init_data.py --import-batch   → 数据库 (全部 withheld)
        ↓
人工/Agent-7 审核             → review_status='approved'
        ↓
init_data.py --publish-batch  → 批量改 published
        ↓
advisors_public_view / v2 接口 → 只读 published
```

测试用快速通道（已在本机演示）：
```bash
# 直接 SQL 把样本置为 published
sqlite3 tsing_radar.db "UPDATE entities SET publication_status='published', review_status='approved' WHERE entity_id IN (...)"
sqlite3 tsing_radar.db "UPDATE claims SET publication_status='published', review_status='approved' WHERE subject_type='entity' AND subject_id IN (...)"
```

## 三、可移植性接入方法（数据库源码在别的设备部署）

### 3.1 设计前提（已实现）

- **零外部服务依赖**：`build_database.py` 只读 `professors_info/*.json`，不调网络、不连数据库
- **跨方言兼容**：迁移文件 0003 已用 `String(36)` + `DateTime(timezone=True)` + `sa.func.now()`，SQLite 与 PostgreSQL 都能直接跑
- **配置驱动**：`DATABASE_URL` 通过 `.env` 注入，换机器只需改一行
- **批次 JSON 可流转**：在 A 机生成 → 在 B 机用 `init_data.py --import-batch` 导入，互不依赖

### 3.2 三种部署形态

#### 形态 A：源码机（采集 + 构建，无数据库）

适合：执行 Agent-1 数据采集工作的设备
```bash
# 1. 把采集结果放到 professors_info/（official_*.json + sources_meta.json + 招生目录_完整.json）
# 2. 运行构建
python3 -m scripts.build_database
# → 输出 data_collection/batches/batch_crawl_<日期>_<id>.json
# 3. 通过受控通道（U 盘/内网传）把 JSON 送到部署机
```
**无需**安装 PostgreSQL / Redis，**无需** alembic。

#### 形态 B：部署机（生产数据库，无源数据）

适合：实际跑 FastAPI 服务的设备
```bash
# 1. 拿到代码（git clone 或拷贝 Tsing-RADAR/backend/）
cd Tsing-RADAR/backend

# 2. 配置 .env
cat > .env <<EOF
DATABASE_URL=postgresql+psycopg2://user:pwd@host:5432/tsing_radar
ADMIN_TOKEN=<强随机>
DOWNLOAD_SIGNING_SECRET=<强随机>
GLM_API_KEY=<可选>
EOF

# 3. 安装依赖（含 PostgreSQL 驱动）
pip install -r requirements.txt
pip install psycopg2-binary

# 4. 迁移
python3 -m alembic upgrade head

# 5. 导入（拿到形态 A 的 batch JSON 后）
python3 -m scripts.init_data --import-batch /path/to/batch_crawl_xxx.json

# 6. 启动
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

#### 形态 C：双机协同（推荐生产）

形态 A 与形态 B 同时存在，通过 batch JSON 解耦：
- 源码机定期产出 batch JSON（含 `captured_at` 增量）
- 部署机定期 `import-batch`（幂等，重复 ID 会更新）
- 审核员在部署机用 SQL 或审核界面把 approved 记录 publish
- 前端只看到 published 数据

### 3.3 ID 稳定性与跨机一致性

- **实体 ID**：随机 UUIDv4，每次 `build_database.py` 运行会重新生成。
  → 若需跨机 ID 稳定，**只在一台机器生成 batch JSON**，另一台纯导入。
- **source snapshot_id / page_content_sha256**：从 `sources_meta.json` 复用，跨机一致（不重新计算）。
- **direction / catalog_link**：每次重建 ID 会变；建议以 batch JSON 为唯一信源。

### 3.4 已做的可移植性约束

| 约束 | 实现 |
|---|---|
| 路径不写死 | `build_database.py` 用 `_PROJECT_ROOT = _BACKEND.parent.parent` 相对定位 |
| 旧路径错误已修正 | `data_loader.py` 改用 `Path(__file__).resolve().parent.parent.parent` |
| Python 3.10+ 兼容 | 用 `Mapped[str]` 但不用 PEP 695 语法（`str \| None` 用 `Optional`） |
| 跨数据库 | 迁移文件无方言特定语法；UUID 用 `String(36)` |
| 配置可注入 | `DATABASE_URL` / `ADMIN_TOKEN` 等全部走 `.env` |
| 批次 JSON 可流转 | 全部数据自包含，无内部引用 |
